The bottleneck wasn't the agent. It was me, watching one.

I had gone through the progression everybody goes through — chat window, then
the IDE plugin, then the command line — and each step was a real improvement.
But they all landed in the same place: one conversation, one task, and me
sitting there while it thought. I could feel the shape of the problem. I had
four or five things I wanted done and exactly one worker.

So I went looking for a way to run several at once, and I ended up somewhere I
did not expect: I tried the obvious tool, could not make it work the way I
needed, and walked back to something much dumber that I built myself.

## The framework I couldn't drive

Early in 2026 I tried [Gas Town](https://github.com/gastownhall/gastown), a
multi-agent workspace manager. It has a whole vocabulary — a **Mayor** who
coordinates, a **Town** that holds your projects, worker agents with persistent
identity, work tracked in a git-backed ledger. Conceptually it was exactly what
I was after.

It did bring many agents to bear on my problems in parallel. That part worked.
What I could not figure out was how to *control* them well. I would set things
in motion and then find I had no good way to steer, correct, or even see what
was happening across the whole town. And so I did the thing you do when a
system is too complicated to drive: I stopped driving it. I ended up sitting and
waiting for the Mayor to do the work — which is precisely the bottleneck I had
set out to escape, now with more moving parts.

<CalloutBox type="tip" title="In fairness to Gas Town">
	It was very new when I tried it, and I probably could have worked harder to
	whip it into the shape I needed. A tool being wrong for me in early 2026 is
	not the same as a tool being wrong. I am describing why I left, not making a
	recommendation about where you should land.
</CalloutBox>

## The two things I took with me

I did not leave empty-handed. Two habits came out of that experiment and both
turned out to be load-bearing.

**tmux.** Not as a terminal multiplexer — as a way to hold several agent
sessions and switch between them in a keystroke. This sounds trivial and it is
not. The cost of checking on an agent has to be near zero, or you stop checking,
and an agent you have stopped checking on is an agent that has quietly gone
sideways for an hour. Fast switching is what makes parallelism actually
parallel instead of just concurrent-and-neglected.

**`--dangerously-skip-permissions`.** The flag does what it says. Every
approval prompt goes away, and the agent just acts.

I understand why that alarms people, so let me say plainly how I think about it.
The prompts were not making me safe. I was approving them the way everyone
approves them — reflexively, in batches, without really reading. What they were
doing was *serializing* the work: the agent stops, I context-switch back, I
click, it resumes. That is the bottleneck again, dressed up as a safety
control.

So I moved the safety somewhere it could actually do some good: **give the
agents great power, and limit the blast radius instead.**

## Where they live

The whole fleet runs inside a single unprivileged LXC container on a Proxmox
cluster. Inside that container the agents have real authority — including
passwordless sudo and control of the lab resources they work on. Outside it,
they have exactly what I have handed them, which is a specific set of
credentials scoped to specific jobs.

That is the trade. Inside the box, the agents are trusted and fast. The box
itself is a container I can snapshot, roll back, or throw away. I would rather
defend one boundary properly than pretend that a thousand approval prompts add
up to a boundary.

It is worth being honest that this is a *homelab* posture. My blast radius is my
own equipment and my own time. If the same fleet were touching production
systems belonging to somebody else, the arithmetic would be different and I
would not be writing this paragraph so cheerfully.

## The day plan

With tmux and no approval prompts, I got to four sessions running in parallel.
And immediately hit the next problem, which is the interesting one: **four
agents working on related things have no way to talk to each other.**

They cannot see each other's conversations. They cannot ask each other
questions. Two of them will happily solve the same problem twice, or worse,
solve it two incompatible ways.

What I built for this is embarrassingly simple. It is a file. I call it the
**day plan**, and it is an append-only log that every agent can write to and
read back. An agent can:

- **propose** an item, which gets an ID
- **ack** somebody else's item, meaning "I've read this and I agree"
- **discuss** under an item, threaded
- set **status** — in progress, blocked, done, disputed
- **render** the current state as markdown

Current state is computed by replaying the log, so several agents can write at
once without stepping on each other. There is no database and no server. The
whole coordination layer is a JSONL file and a Python script.

<CalloutBox type="tip" title="Why append-only turned out to matter">
	My first instinct was a shared markdown file the agents would edit. That
	fails immediately and in the most annoying way: two agents read it, both
	edit, the second write silently erases the first, and neither of them knows.

	Append-only fixes it at the storage layer instead of asking everyone to be
	careful. Nobody edits; everybody appends; the current picture is derived. It
	is the same reason the shared host inventory ended up as one file per host.
</CalloutBox>

The rhythm that grew around it is my favorite part of all this. I would wake up
having slept on the previous day's work, and I would have new tasks — usually
with some dependency between them that we would refine as the day went on. The
day plan is where I put those, and where the agents put their results, their
requests of each other, and their proposed follow-ups.

It reads like a stand-up that happens in writing, all day, without anybody
standing up.

<CalloutBox type="warn" title="The failure mode is stale reads">
	The single most common way this breaks is an agent working from a rendered
	copy it made an hour ago and concluding that nobody has responded to it. The
	log is the truth; anything you rendered from it is already history. Every
	agent's instructions now say so explicitly, because I lost an afternoon to it
	before I worked out what was happening.
</CalloutBox>

## Then I went looking for how state actually works

Here is the part I got to backwards. I had been running this fleet for a while
before I understood how any of the underlying state was shared — I just had a
strong instinct that I wanted the work **partitioned into distinct contexts**,
so each agent kept a small, focused working set and needed compaction less
often.

The analogy I kept coming back to is hiring.

Say you run a ten-person company and everyone is working at 90% capacity. On
paper you have one person's worth of slack — you could distribute the new
project across the team and it would fit. But you probably should not. Handing
a new direction to ten busy people costs each of them a context switch, and the
work you actually get is worse than one focused person's. **Hire the eleventh.**

That is exactly the trade with agents, except the eleventh employee costs
nothing and starts immediately. If a new domain is genuinely a new domain, it
should get its own agent rather than being pushed into somebody's already-full
head.

So I eventually pointed an agent at the fleet itself — a meta agent whose whole
job is how the other agents are set up — and had it work out what was really
going on. Three things are keyed independently:

| what | where it lives | keyed by |
|---|---|---|
| the conversation transcript | on disk, per project | the directory you launched from |
| the instructions | `CLAUDE.md` in the project, plus a global one | the project directory |
| the distilled memories | a memory store per project | **the git repo**, if there is one |

Which yields one rule that does most of the work:

> **Launch each agent from its own directory, and it gets a separate transcript,
> separate instructions, and separate memory for free.** No access control
> needed. The isolation is a side effect of where you started.

That third row is the one that bit me. The memory store keys to the *git
repository* the launch directory sits in, not the directory itself — and my home
directory had accidentally become a git repo, left over from the earlier
experiment. So every agent beneath it was pooling its memories into one shared
store and reading everyone else's facts. The fleet had been quietly leaking
context between agents for weeks, which is the precise opposite of what I was
trying to build. Archiving that stray `.git` fixed it.

<CalloutBox type="warn" title="Isolation of context is not isolation of authority">
	The directory boundary separates what agents *know*. It does nothing about
	what they can *reach* — they all run as the same user, with the same skipped
	permissions. An agent's actual blast radius is set by the credentials I hand
	it, and nothing else.

	So the two axes have to be reasoned about separately, and the credential is
	the one that matters. Scope it to the job.
</CalloutBox>

## Where it stands

There are about a dozen agents now. Four of them are sessions on my main
research project, working in separate git worktrees on the same repository and
coordinating through the day plan. The rest are one-per-domain — the network
gear, the monitoring stack, the DNS, the UPS fleet, this blog — plus a couple of
private, non-technical ones that will not be appearing in any post.

The blog agent is the interesting edge case, because it is the only one whose
output leaves the box. Every other agent's discipline is about what it can
touch. That one's discipline is about what it can *reveal*, which turns out to
be a completely different review.

## What I'd tell someone starting

**Steal the tmux habit first.** It is free and it changes the economics of
watching more than one thing.

**Build the shared file before you think you need it.** The moment you have two
agents on related work, you have a coordination problem, and you will invent
something worse under time pressure than what you would design calmly.

**Make it append-only.** Whatever it is.

**Partition by domain, not by capacity.** The temptation is to give new work to
whichever agent seems least busy. Resist it. Hire the eleventh.

**And pick your boundary deliberately.** Somewhere between "approve every file
write" and "no limits at all" there is a line that fits what you are actually
risking. Mine is the edge of a container I can roll back. Yours might be
somewhere else entirely — but it should be a decision you made once, not a
prompt you dismiss forty times a day.
